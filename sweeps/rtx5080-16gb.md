# Ternary Bonsai 2 27B, RTX 5080 16GB

All numbers from one RTX 5080 16GB (Blackwell, sm_120) on Linux, one machine, one session,
2026-09-25, single slot, q4_0 K/V cache, flash attention on, `-ngl 99`, driver 610.57.04
(CUDA UMD 13.3), AMD Ryzen 7 5800X3D. The card also drives the desktop: 1,242 MiB in use
before any run. Numbers only from runs done on this machine.

This is the 16GB row that `serve/README.md` lists as pending, and the first Blackwell row.

## Short version

- **On Blackwell the `pr-ptq1-mmv` branch at `285542d` produces garbage as served.** `llama-bench`
  runs at full speed, but in `llama-server` the text breaks a few tokens in, into `!!!!` or `////`
  (text and vision alike). Cause: the new PTQ1_0 mat-vec kernel is launched through
  `ggml_cuda_kernel_launch`, which opts into PDL on Hopper and newer, and the kernel never calls
  `ggml_cuda_pdl_sync()`, so it can read `vy` before the q8_1 quantize kernel has written it.
  Ampere and Ada never take the PDL path, which is why the 3060, 3060 Ti and 4070 rows are clean.
  One line fixes it (below); `GGML_CUDA_PDL=0` or `GGML_CUDA_DISABLE_GRAPHS=1` also work around it.
- With that line added: **decode +10.8% fresh, +5.7% at 131K** over the newest PrismML release.
  The gain is far smaller than on the 3060 (+53%): at 960 GB/s the stock kernel is already
  less starved than it is at 360 GB/s.
- **The full 262K window fits with the vision tower**: 12,684 MiB for the server process.
  `serve/16gb-vision.sh` could move from 131072 to 262144.

## The PDL fix

```diff
--- a/ggml/src/ggml-cuda/mmvq-ptq1_0.cuh
+++ b/ggml/src/ggml-cuda/mmvq-ptq1_0.cuh
@@ -298,6 +298,10 @@ static __global__ void mul_mat_vec_ptq1_0_pt(
     const void * GGML_CUDA_RESTRICT vx  = vx_ptr;
     const void * GGML_CUDA_RESTRICT vy  = vy_ptr;
     float      * GGML_CUDA_RESTRICT dst = dst_ptr;
+    // launched through ggml_cuda_kernel_launch, which opts into PDL on Hopper and newer: wait for the kernel
+    // that wrote vy (the q8_1 activation quantization) before reading it
+    ggml_cuda_pdl_sync();
+
     extern __shared__ float partials_dyn[];
```

The stock `mul_mat_vec_q` kernels in `mmvq.cu` make the same call before they read.

How it was isolated: a greedy request (`temperature 0`, `top_k 1`, thinking off, "In two
sentences, what is a GPU?") through `llama-server` at 32K, q4_0 K/V:

| build, environment | output |
| --- | --- |
| b10685 or b10735 | `A GPU (Graphics Processing Unit) is a specialized processor designed to handle …` |
| `285542d` as is | `A GPU (Graphics Processing!!!!!!!!!!!!!!!!…` |
| `285542d`, `GGML_CUDA_BATCH_INVARIANT=1` | `A GPU (!!!!!!!!!!!!!!!!…` |
| `285542d`, `-fa off` | `A GPU!!!!!!!!!!!!!!!!…` |
| `285542d`, `GGML_CUDA_DISABLE_GRAPHS=1` | correct |
| `285542d`, `GGML_CUDA_PDL=0` | correct |
| `285542d` + fix | correct, identical to b10735 |

`test-backend-ops -o MUL_MAT -b CUDA0` passes every PTQ1_0 case on this card with the unfixed
build. Each test case runs its op on its own, so it never races a preceding kernel, and it
cannot catch this bug. The same image prompt (a screenshot of the model card) described the
card correctly on b10685, b10735 and kernel+fix, and broke into `!!!!` (thinking off) or `////`
(thinking on) on the unfixed build.

After the fix, a 400-token greedy code prompt matches b10735 for the first 163 characters,
then takes the other side of a near-tie. Both outputs are coherent and correct. This is the
reduction-order difference the README describes for the branch; it is not the bug.

## Notes

- Thinking trap, vision edition: at `--reasoning-effort medium`, the image prompt spent
  4,096 and then 16,384 tokens in `<think>` on the unfixed build. That was the PDL bug
  producing `////`, not the model thinking. On the fixed build, at 262144 with vision and the
  `16gb-vision.sh` sampling flags, the same prompt thought for 1,110 characters and answered in
  999 tokens at 94.2 tok/s, prefill 1,324 tokens at 1,199 tok/s, reading the numbers off the image
  correctly.
- Build trap: a conda-forge toolchain on a rolling distribution fails to link
  `libllama-common` against the system OpenSSL (`libcrypto` needs Brotli symbols the conda
  sysroot does not have). `-DLLAMA_OPENSSL=OFF` avoids it; nothing here needs HTTPS.
